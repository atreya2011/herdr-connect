### Discord topology synchronization cost

The startup sweep fetches guild channels and active threads once at its start into a mutex-guarded `TopologyCache`, reusing that pair across every tab it syncs instead of refetching per tab. The delivery path (`sync_route`) now serves a route straight from that cache when it already holds the route's workspace channel and tab thread, and refetches only when the cache is empty or does not yet hold the route. A send against a cached thread that fails as an unknown channel clears the cache and logs; the next event resolves the route again through the cache-first path, rather than re-resolving and retrying inside the same call. The lock is held for the whole call so concurrent requests still serialize correctly instead of racing a duplicate create. The permission path (`sync_channel`) still fetches a fresh pair on every call; port the same cache-first behavior there only with its own real-service tests, not by assuming this note is enough. Preserve the outcome of [historical issue #27](https://github.com/atreya2011/herdr-connect/issues/27): ordinary checks read the fetched lists, while archived-thread listing is a miss-path HTTP read, skipped whenever the active list already resolves the tab. Port the behavior, not the old discord.js implementation details.

Slack caches tab channels separately and queues name reconciliation and channel closure in background tasks. Startup reads fresh Herdr workspace and tab lists after syncing routes, immediately before loading channels for orphan cleanup. A route, archive, or invalid-label failure is logged without skipping other resources or name reconciliation.

## Preserved product contracts

- Discord uses one workspace channel per mirrored Herdr workspace and one tab thread per mirrored tab. Slack uses one public channel per mirrored tab, with no workspace channel or bot thread-parent message; the owner is invited to each new channel.
- A pane whose Herdr integration reports no session identity has no tab conversation or cards until a later snapshot reports one. Its Discord workspace channel may exist for another pane with a session; Slack creates no channel for that session-less tab.
- Discord identity is the workspace channel topic and tab thread suffix. Discord channel names follow the Herdr workspace label and thread names follow the tab label; workspace and tab renames and startup reconcile those names in background tasks, so Discord's rename limit does not block messages. Slack identity is the workspace and full tab IDs in its channel topic. Slack channel names combine workspace label, workspace ID, tab label, and short tab ID; workspace and tab renames and startup reconcile those names. Names retain Unicode letters and numbers; labels are shortened by characters to fit Slack's 80-character limit, and IDs are preserved. Rate-limited renames and channel closure run in background tasks so messages continue. Owner renames run the other way: an owner rename of a Slack tab channel or a Discord tab thread renames the Herdr tab, and an owner rename of a Discord workspace channel renames the Herdr workspace. Renames by anyone else, and names the bridge itself sets, change nothing.
- Reported vendor sessions provide content; pane scraping and guessed session paths are forbidden, except for reading a Claude pane's Herdr detection snapshot to extract a pending blocked question and to confirm the dialog is still showing before an answer is typed.
- Only blocked, permission, and question cards mention the owner. Discord uses explicit mention allowlists; Slack escapes message text and emits explicit mentions in its cards. Working and done post no cards; Slack attaches assistant working status to the latest accepted owner message, keeps it set while any pane in the tab works, and clears it when work stops. Status API failures are logged without failing an accepted prompt or a successful message post.
- Owner-only semantic prompts inside mapped Discord tab threads or Slack tab channels; unrelated chat surfaces and bot messages are ignored. Slack decodes message entities, links, and mentions before submitting text. Prompt-submission and free-text-answer acknowledgements are ephemeral to the owner. Empty multiple-choice submissions receive an ephemeral refusal and leave the question card open; question cards show their header and option descriptions.
- Terminal prompts are mirrored with the owner's display name and avatar: through a Discord webhook or a customized Slack bot message. Both adapters fetch the profile once at startup; a failed Slack profile lookup stops startup. Slack requires `users:read` and `chat:write.customize` for this behavior.
- Both adapters default to test-only scope; the no-argument, `slack`, and standalone `broker` entry points explicitly select service scope. The production bridges additionally enable `testrun-` exclusion; standalone `broker` leaves that exclusion disabled. Test-only scope accepts messages, buttons, deletions, and archives only on test chat resources mapped to a `testrun-` Herdr workspace or tab; production events receive no handler call or acknowledgement. Discord test deletion registries hold only test workspace channels and their tab threads. Read-only service listings may include production resources to check that tests preserve them.
- Permission decisions are correlated, expiring, exactly once, and invalid when the requesting hook disconnects.
- Discord deletion is two-way. A closed Herdr tab's thread is deleted; a closed Herdr workspace's channel is deleted (Discord removes its threads with it). An owner-deleted tab thread closes its Herdr tab (`herdr tab close`), and an owner-deleted workspace channel closes its Herdr workspace (`herdr workspace close`). Owner deletion is proved only by a guild audit-log entry of the matching type whose target is that thread or channel and whose user is the owner; any other deletion, no matching entry, or a failed audit-log request closes nothing. The gateway's thread-delete event carries no name, so the tab is resolved from a durable registry of bridge-owned thread ids (filled from in-scope active and archived listings and creates, never cleared by cache invalidation); a thread the registry does not hold is not a live tab's thread and is ignored with no Herdr call and no notice. Archived threads are registered at startup per in-scope channel, independent of the delete pass; a failed listing is logged. Startup deletes in-scope workspace channels and tab threads absent from Herdr: the production bridge exclusion preserves `testrun-` resources, and test-only scope preserves production resources. Discord deletes obsolete topology rather than archiving it.
- Slack closes a Herdr tab only when its channel-archive event identifies the owner. Other actors and deletion events without owner proof close nothing; no Slack channel event closes a workspace. Closing a Herdr tab renames and archives its channel; closing a workspace does so for all its tab channels. Startup also renames and archives in-scope orphaned tab channels and legacy workspace channels. Renaming before archive releases the original name for reuse; archived channels remain in Slack.
- A tab with a numeric label is renamed once to a generated `word-word-word` label before it is routed; a rename that fails is logged and the tab is not mirrored until it succeeds.
- One watcher per pane, four rules: (1) a session-carrying pane appears -> create its Discord tab thread or Slack tab channel and follow its vendor log from its saved reading positions, or the current end when there are no saved positions, or from 0 if the log does not exist yet; (2) the log gains complete assistant text -> post it as a plain message (never a tool call), per log position, whatever the pane's status; (3) the pane goes blocked -> post the blocked, permission, or question card, while working and done post no cards; (4) the pane closes or its session resolves to a different log -> close the watcher, the only time one closes. A restart resumes saved prompt and assistant reading positions and posts messages written during downtime once. Discord and Slack keep separate positions. Discord additionally suppresses exact repeats within its nonce window using a position-derived nonce; Slack does not use that nonce.
